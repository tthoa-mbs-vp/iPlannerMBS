## 1. Tóm tắt điều hành

App đã rất chín muồi về **bảo mật backend** và **kỷ luật kiến trúc**: 3 lớp quyền (API rules → field-level guards → view-scope hooks fail-closed), audit hoàn toàn server-side chống giả mạo log, chấm công chống gian lận (server-stamp + IP thật), KPI server-computed, kèm bộ integration test backend chạy PocketBase binary thật. Đây là nền tảng hiếm có ở một sản phẩm nội bộ.

Phần còn thiếu tập trung vào 3 nhóm:

1. **Bảo mật còn lỗ hổng cụ thể, sửa được ngay (P0):**
   - `xlsx@0.18.5` (npm) dính **CVE-2023-30533** (prototype pollution, CVSS 7.8) — app **parse file Excel người dùng upload** nên đây là đường tấn công thật, không phải lý thuyết.
   - `web/.env` đang được **commit vào git** (trong khi `.env.local` mới bị ignore) — nguy cơ lộ credential.
   - Upload avatar cho phép `image/svg+xml` — vector stored-XSS cùng origin.
   - `sanitizeHtml` tự viết tay thay vì thư viện đã kiểm chứng (DOMPurify).

2. **Vận hành / phát triển (P0–P1):**
   - `backend/pb_migrations/` **không tự khởi tạo được** một instance mới (thiếu `created_*` cho các collection nền; còn migration dev-leftover `deleted_t1`/`created_probe_col`; hardcode record id của DB local). Đã có script cứu trợ (`bootstrap-schema.mjs` + `sync-schema.mjs`) nhưng cần CI test chặn tái phát.
   - **Chưa có CI/CD** dù `package.json` đã có sẵn script `ci` và bộ 6 file integration test backend rất giá trị — hiện chỉ chạy được bằng tay qua Makefile.
   - `docker-compose.yml` dùng `npm install` thay `npm ci`; `backend/docker-compose.yml` dùng tag `:latest` không pin.

3. **Kiến trúc dữ liệu (P1):**
   - Công thức KPI **trùng lặp client/server** (`web/src/utils/kpi.ts` vs `helpers.js upsertKpi`) — rủi ro lệch điểm khi sửa một bên.
   - `view_scope` lọc **in-memory sau phân trang** (tradeoff đã ghi chú trong ARCHITECTURE.md) — `totalItems` và số trang không khớp thực tế, chi phí DB tăng theo dữ liệu.
   - `getFullList` không giới hạn ở nhiều hook dữ liệu.

## 3. Phát hiện & đề xuất

### 3.1 P0 — Bảo mật (nên xử lý trong tuần đầu)

#### 🔴 3.1.1 `xlsx@0.18.5` dính CVE-2023-30533 (prototype pollution, CVSS 7.8)
- **Vấn đề**: `web/package.json` khai báo `"xlsx": "^0.18.5"` — phiên bản npm cuối cùng. CVE-2023-30533 ảnh hưởng mọi bản SheetJS CE ≤ 0.19.2 (prototype pollution khi đọc file độc hại + ReDoS); bản vá 0.19.3 **không phát hành lên npm** (chỉ qua CDN SheetJS). App **parse file Excel do người dùng upload** ở luồng import admin (`web/src/services/dataService.ts`, `web/src/utils/importExport.ts` dùng `XLSX.read`), nên file độc hại là vector tấn công trực tiếp.
- **Đề xuất**:
  1. Chuyển sang bản vá từ CDN chính thức: `"xlsx": "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz"` (giữ nguyên API, xoá được cảnh báo audit), **hoặc** thay bằng `exceljs` nếu không muốn phụ thuộc CDN.
  2. Thêm validate trước khi parse: giới hạn kích thước file (vd ≤ 10 MB), kiểm tra MIME/extension, đọc qua `File.arrayBuffer()` rồi `XLSX.read` với `type: "array"`.
  3. Thêm `npm audit` vào CI để chặn tái phát.

#### 🔴 3.1.2 `web/.env` bị commit vào git
- **Vấn đề**: `.gitignore` chỉ ignore `.env.local`, còn `web/.env` **đang được track** (`git ls-files` ra `web/.env`) — file này chứa giá trị dev (có thể gồm `PB_ADMIN_*`, URL nội bộ…). Nếu nó từng chứa mật khẩu, secret đã nằm trong lịch sử git.
- **Đề xuất**:
  1. Thêm `web/.env` vào `.gitignore` (giữ `web/.env.example` với key trống làm mẫu).
  2. `git rm --cached web/.env` (giữ file ở đĩa).
  3. Nếu file có chứa mật khẩu admin/PB seed → **đổi mật khẩu** (coi như đã lộ).

#### 🔴 3.1.3 Avatar cho phép `image/svg+xml`
- **Vấn đề**: DATA_DICTIONARY.md `users.avatar` whitelist gồm `image/svg+xml`. SVG cùng origin được serve qua `/api/files/...` có thể chứa `<script>` — nếu trình duyệt mở inline (hoặc bị `img src` cấm script nhưng mở trực tiếp URL thì chạy) là stored-XSS.
- **Đề xuất**: bỏ `image/svg+xml` khỏi whitelist (PNG/JPEG/WebP là đủ), hoặc nếu bắt buộc giữ thì đảm bảo PB serve với `Content-Disposition: attachment` và thêm CSP (`img-src` không cần thay đổi, nhưng cấm script từ `blob:`/file origin). Đây là thay đổi migration + rules nhỏ, rủi ro thấp.

#### 🟠 3.1.4 `sanitizeHtml` tự viết tay
- **Vấn đề**: `web/src/utils/sanitize.ts` tự xoá tag/attribute theo danh sách — không qua thư viện đã kiểm chứng; còn giữ attribute `style` (dùng được cho CSS-exfil `background:url(...)`) và có thể bị bypass bằng các pattern chưa liệt kê.
- **Đề xuất**: thay bằng `DOMPurify` (`dompurify`) — chuẩn ngành, nhỏ (~7 KB gzip), API tương đương. Giữ hàm wrapper `sanitizeHtml` để khỏi đổi chỗ gọi.

#### 🟠 3.1.5 Rate limiting cho auth + CSP
- **Vấn đề**: chưa thấy cấu hình rõ ràng rate limit cho `/api/collections/users/auth-with-password` (PocketBase 0.39 có rate limit mặc định, nhưng nên kiểm tra `pb_settings` đang thực tế bật mức nào); `index.html` không có CSP.
- **Đề xuất**: kiểm tra/điều chỉnh rate limit auth qua API settings (vd giới hạn thấp hơn cho auth path); thêm CSP cơ bản vào `index.html` (ít nhất `default-src 'self'`, `script-src 'self'`, `img-src 'self' data: blob:`), kiểm tra không phá luồng realtime/WebSocket của PB.

### 3.2 P0 — Vận hành & phát triển

#### 🔴 3.2.1 `pb_migrations/` không tự khởi tạo instance mới
- **Vấn đề**: các collection nền (departments, roles, users, plans, tasks, proposals, comments, kpi_scores, notifications, system_logs…) **không có migration `created_*`** — chỉ có `updated_*` giả định schema đã tồn tại; còn `1785834026_deleted_t1.js` / `1786604164_created_probe_col.js` là migration dev-leftover xoá/tạo collection thử nghiệm, và một số migration hardcode record id từ DB của dev. Hệ quả: **bất kỳ instance PocketBase mới nào (hosting, CI, máy đồng nghiệp) đều crash khi boot** — docker-compose hiện chạy được chỉ vì mount `pb_data/` cũ.
- **Đã làm (giảm nhẹ)**: `web/scripts/bootstrap-schema.mjs` (tạo đủ 27 collection theo DATA_DICTIONARY.md, idempotent) + `web/scripts/pb-schema.json` (schema chuẩn) + `web/scripts/sync-schema.mjs` (import vào instance đích) — **đã kiểm chứng trên PocketBase 0.39.10 thật** (boot fresh → import → hooks nạp 0 lỗi → seed → login OK).
- **Đã làm (chặn tái phát — triển khai đầy đủ)**:
  1. ✅ **`created_*` migrations chính thức cho 9 collection nền** + sync `users` — sinh bởi `web/scripts/gen-created-migrations.mjs` từ `pb-schema.json` (tái sinh idempotent). Id dùng đúng id chuẩn mà các `updated_*` tham chiếu; relation được đổi id tương ứng; các relation tới collection chưa tồn tại (`plans.group_id`, `users.group_ids`, `comments.quote_id`) hoãn sang migration sau target.
  2. ✅ **23 migration cũ guard idempotent** (skip add nếu field đã có / skip remove nếu không tồn tại); **2 dev-leftover vô hiệu hoá** (`deleted_t1` no-op khi không có collection, `created_probe_col` không tạo nữa); record-op đã có try/catch từ trước.
  3. ✅ **CI boot test**: job `backend` tải PB 0.39.10 → chạy 3 integration tests trên instance **fresh-boot từ migrations** (không cần `pb_data`); harness test đổi từ copy `pb_data` sang thư mục trống + migrations.
  4. ✅ **`pb-schema.json` tái xuất chuẩn** từ instance boot-by-migrations (bổ sung `created/updated` autodate + toàn bộ index — snapshot cũ thiếu vì PB không tự thêm khi tạo qua API).
  - Kiểm chứng: fresh boot 90 migrations + hooks → schema khớp snapshot (27 collection, rules, fields, indexes); boot lần 2 idempotent; harden 29 + scope 11 + audit 12 = **52 assertion pass**.
  - Lưu ý: instance tạo từ snapshot cũ (id `pbc_departments` dạng tên) sẽ không tương thích id chuẩn — chỉ ảnh hưởng DB thử nghiệm, không có deployment thực nào dạng đó.

#### 🔴 3.2.2 Chưa có CI/CD
- **Vấn đề**: không có `.github/workflows/`; script `npm run ci` (typecheck + lint + test + build) và 6 file integration test backend chỉ chạy tay. Không ai chặn được regression về type/lint/rule bảo mật khi merge.
- **Đề xuất**: GitHub Actions với 2 job:
  1. **web-ci**: `cd web && npm ci && npm run ci`.
  2. **backend-ci**: tải PocketBase 0.39.10 binary (như `backend/Dockerfile`) vào thư mục tạm, chạy `node backend/test/*.test.js` với `PB_BIN` trỏ tới binary (Makefile đã có sẵn cơ chế này cho Windows/podman — mở rộng cho Linux runner).
  Kèm `npm audit --audit-level=high` trong web-ci (bắt được mục 3.1.1 sau khi vá).

#### 🟠 3.2.3 Docker: `npm install` và tag `:latest`
- **Vấn đề**: `docker-compose.yml` (web service) chạy `npm install` mỗi lần start — chậm và không tái lập được (đã có `web/package-lock.json`); `backend/docker-compose.yml` dùng `pocketbase/pocketbase:latest` không pin, thiếu healthcheck — môi trường "backend-only" có thể lệch version với `backend/Dockerfile` (0.39.10).

### 3.3 P1 — Kiến trúc & hiệu năng dữ liệu

#### 🟠 3.3.1 Công thức KPI trùng lặp client/server
- **Vấn đề**: `web/src/utils/kpi.ts` (`calculateKpi`) và `backend/pb_hooks/helpers.js` (`upsertKpi`) cùng triển khai công thức (base 10/12 × 0.3×schedule + 0.7×rating × hệ số khó) ở **2 nơi, 2 ngôn ngữ** — sửa một bên là lệch điểm, không có test bắt.
- **Đề xuất**: chọn server làm nguồn chân lý; bỏ logic tính phía client hoặc thay bằng **endpoint preview KPI** (`POST /api/custom/preview-kpi` — đã có sẵn pattern `recalc-kpi`); thêm test chéo so sánh kết quả client vs server trên cùng bộ input.

#### 🟠 3.3.2 `view_scope` lọc in-memory sau phân trang
- **Vấn đề**: `scope.pb.js`/`hr.pb.js` lọc **trong hook sau khi PB đã phân trang** — `totalItems` không khớp số bản ghi thực trả về, trang có thể "rỗng" trong khi tổng vẫn báo đầy; đồng thời server vẫn phải đọc toàn bộ bản ghi pass `listRule` rồi mới lọc (chi phí tăng theo dữ liệu). Tradeoff đã được ghi chú trong ARCHITECTURE.md.
- **Đề xuất (ưu tiên theo thứ tự)**:
  1. Nếu được, chuyển scope vào **`listRule` động** (PocketBase 0.39 hỗ trợ biểu thức `@request.auth.role_id...` trong rule — nhiều collection đã dùng) để lọc ngay tại SQL, giữ đúng phân trang.
  2. Nếu giữ lọc in-memory: thêm **index** cho các field lọc chính (`plan_id`, `executor_id`, `supervisor_id`, `department_id`), và ở frontend tránh dựa vào `totalItems` cho phân trang (dùng số trang hiển thị thực tế).
  3. Ghi rõ giới hạn này vào docs deploy để không ai ngạc nhiên khi data lớn.

#### 🟠 3.3.3 `getFullList` không giới hạn
- **Vấn đề**: nhiều hook frontend (`useTasks`, `usePlans`, `useSystemLogs`, `useAttendance`…) dùng `getFullList` — load toàn bộ bản ghi; hiện đã có cron archive 6 tháng nên tạm ổn, nhưng `system_logs` (audit) và attendance sẽ phình nhanh theo thời gian.
- **Đề xuất**: với các danh sách lớn (logs, attendance history, reports), chuyển sang `getList` + phân trang server-side hoặc infinite query; giữ `getFullList` cho các entity giới hạn trong phạm vi cá nhân.

#### 🟠 3.3.4 Token auth trong localStorage
- **Vấn đề**: PocketBase SDK mặc định lưu JWT trong `localStorage` — nếu có XSS là mất session. (Đã có sanitize + remember-me 2 chế độ, nhưng chưa có CSP để giảm diện tích XSS.)
- **Đề xuất**: kết hợp với mục 3.1.5 (CSP); nếu sau này triển khai sau proxy, cân nhắc cookie `httpOnly` + `SameSite` thay vì localStorage.
